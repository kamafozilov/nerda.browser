# Technical decisions

Reference: [driceroland/Search](https://github.com/driceroland/Search) (MIT). We follow the same path.

## Adopted

| # | Layer | Decision | Why |
|---|---|---|---|
| 1 | Platform | macOS only | I use macOS myself; on Windows/Linux, Chrome extensions only fully work with Chromium, which goes against the "lightweight" goal |
| 2 | Engine | WebKit (`WKWebView`) | Ships with the system: the app is a few MB, without Chromium's 300 MB |
| 3 | Language | Swift | The only natural choice for Apple APIs |
| 4 | UI | SwiftUI, plus AppKit where needed | Search does it this way and it works |
| 5 | Project | SwiftPM (`Package.swift`) + `build.sh` assembles the `.app` bundle | Plain text files only; Xcode not required (Command Line Tools are enough) |
| 6 | Minimum OS | macOS 15.4 | `WKWebExtensionController` exists from this version on (checked in a build) |
| 7 | Chrome extensions | `WKWebExtension` + installing `.crx` from the Chrome Web Store, after Search: the store's page gets an Add to Nerda button (`WebStore.swift`); the CRX3 signature is checked against the extension's id before unpacking (`Crx.swift`); a script put in each extension at install fills in the Chrome APIs WebKit lacks and mends where it differs (`ExtensionShims.swift`); popups are Nerda's own popover. Buttons at the right of the address bar, as in Chrome. The regular window's tabs only, not incognito. Turned off in every build for now (`Extensions.available`, 2026-10-14): no controller, store button, address bar button or settings page, whatever the saved switch says. Installed extensions and their settings stay on disk for when it turns back on | Speed and reliability take priority over Chrome compatibility. That is where the main users come from. Search's layer is the working answer to WebKit's gaps; a popup's page goes by its own address (Dark Reader answers only that), and hears the worker's messages over a channel, which WebKit keeps from it |
| 8 | Ad blocking | EasyList and EasyPrivacy filters compiled to `WKContentRuleList` in a helper process, refreshed every 4 days in the background (`NSBackgroundActivityScheduler`, never at launch unless there is no list yet), asking only for lists changed since (ETag, Last-Modified) and compiling only when the lists or Nerda changed. Network filters block loads; element-hiding filters (`##`, `domain##`, `~domain##`) become `css-display-none` rules in lists of their own, one rule per selector, after their `#@#` exceptions are applied; `$elemhide`, `$generichide` and `$document` exceptions turn all hiding off on those pages; uBlock's and AdGuard's own selectors (`#?#`, `+js`, `:has-text`…) are skipped. Main-frame navigation is always allowed by ad lists; the lists of dangerous sites (Phishing URL Blocklist, Online Malicious URL Blocklist, uBlock filters – Badware risks, CERT.PL's Warning List) are compiled into lists of their own without that exemption, their `$doc` blocks kept, so a site on them is refused as a page, and the tab says which list it is on and that the site's Ads and trackers switch lets it open. Generic blocks apply only to third-party requests, and known challenge services are exempt. Settings can disable blocking. See [adblock audit](adblock-audit.md) for translation limits and evidence | WebKit filters requests and hides elements without per-request Swift or JavaScript. Versioned compiled caches prevent reuse of unsafe rules; failed updates keep the last compatible list, and navigation never waits for a download. WebKit's ignore-previous-rules undoes everything before it in its own list, hiding included, so hiding and the dangerous sites live in lists the page exemption isn't in. Scriptlets and procedural cosmetic filters are not supported |
| 9 | RAM | Put unused tabs to sleep (the web view is destroyed, a snapshot stays) after 30 minutes out of sight (Settings › Tabs: 15 minutes to 4 hours, or never), except a tab switched to more than 15 times, and after 10 minutes when one takes over 500 MB. Under memory pressure (`SleepCoordinator`, spec #118): a warning puts nothing to sleep; critical pressure puts the heaviest eligible tab of any window to sleep, then one more every 5 s until it ends. Never eligible: the tab on screen, the last five tabs used in its window, a tab seen in the last 10 minutes or heard in the last minute, an edited page, active media capture. `NERDA_PRESSURE_POLICY=0` brings back the old rule for one run (every hidden tab at once, pinned ones too when critical). Edited pages and active media capture stay awake. Pinned tabs load at launch after the tab on screen, one at a time, or not until opened (Settings › General); they sleep only under critical memory pressure, with the same protections, or when one takes over 500 MB | 100–300 MB per tab is the main cost. The same six sites took 1.63 GB in Nerda and in Safari alike (2026-09-26): what was left was pinned x.com and Gmail at 650–750 MB each, never asleep, and one WebGL tab at 2.2 GB. Every hidden tab at once on a memory warning made the tabs just used reload for a short spike; one at a time, heaviest first, with Chrome's and DuckDuckGo's protection times, gives back as much memory with as few reloads (Yab, from the same Search fork). The last five are per window, from each window's own order of tabs on screen |
| 10 | Storage | JSON files, in one folder. A window's tabs are `session.json` (secondary windows' in `Windows/`), written soon after each change; its recently closed tabs, whose pages' state is most of the size, a file of their own beside it (`.closed`), written only when they change. Each session read at launch is copied beside it as it was (`.previous`): renamed back over the session, it brings the tabs back should a wrong state have been saved | No server, no account. One file for both rewrote ~600 KB of closed tabs' state with every scroll and tab switch |
| 11 | Passwords (the Vault) | Nerda's own store: the passwords, with their notes, are one item in the login keychain (`Nerda Passwords`), the site and user names they go with are `accounts.json` beside the history; those in Passwords/Safari come in once from a CSV via File › Import Passwords…, and go out again as Chrome's CSV from the Vault. A sign-in with another service (Google, GitHub, Telegram…) is kept the same way, with the service in place of a password (`SocialSignIn.swift`): an OAuth/OpenID request to a known service from a site's page starts it, the service's answer to that site without an `error` brings it back, and a page of the site that asks for no password (or the service's pop-up closing itself) is the sign-in done | Safari's passwords sit behind an Apple entitlement; macOS (AMFI launch constraint) won't start the iCloud Passwords helper from Nerda. The keychain asks again after every build without a Team ID: as one item, and with the names outside it, that is one question, and only once a password is picked or saved, never for listing accounts. A sign-in with a service has no password to see, so it is told by where the page goes, which needs no script on the service's pages but one that tells Google's chosen account |
| 12 | External dependencies | None, Apple frameworks only | |
| 13 | Codebase | Written from scratch; needed parts (e.g. `Crx.swift`, `ExtensionShims.swift`) are taken from Search, with the MIT license text | The structure should be our own |
| 14 | Tools | Xcode (Instruments, debugger), `swift format` (in the toolchain) | Command Line Tools are enough to build |
| 15 | Entry point | AppKit (`NSApplication`, `main.swift`); SwiftUI views through `NSHostingView` | Full control over windows; a SwiftUI `App` always requires some Scene |
| 16 | Concurrency | Swift 6.2, default isolation `MainActor`, with approachable concurrency (`NonisolatedNonsendingByDefault`, `InferIsolatedConformances`): a `nonisolated` async function runs on its caller's actor, and work that must leave the main thread is marked `@concurrent` | AppKit and WebKit are on the main thread anyway; background work is marked explicitly |
| 17 | Versions | SemVer tags `vX.Y.Z`; 0.0.x, one patch step per release, until the public launch as 1.0.0; `CHANGELOG.md` in Keep a Changelog form | See [releasing.md](releasing.md) |
| 18 | Dev and release | Nerda Dev (debug) is a separate app: its own bundle id, data folder and keychain item (`Edition.swift`, `build.sh`) | Working on Nerda must not touch the data of the Nerda in use |
| 19 | Updates | Our own updater (`Updater.swift`, after Search's): GitHub Releases carry the DMG and a ZIP; a newer ZIP is checked by SHA-256, bundle id, version and a Developer ID signature of the same team, its certificate checked for revocation as it arrives (and again offline as it is swapped in, so quitting never waits on the network), then swapped in | No framework (#12): Sparkle would add a framework, an EdDSA key and a copy step to build.sh, for what about 300 lines do |
| 20 | Signing | Releases: Developer ID Application, one fixed team (`NERDA_TEAM` in the untracked `release.env`), hardened runtime, notarized and stapled, universal (arm64 + x86_64). Development: the Apple Development certificate, as before | Opens on any Mac without warnings; the team is fixed because the updater only accepts its own |
| 21 | New tab pictures | CC0 photos from Wikimedia Commons, bundled (`assets/backgrounds`, credits there), 2880 px HEIC, one for now, more as they are chosen; one a day, decoded once off the main thread, big enough to fill the largest screen. Your pictures are copied into the data folder (`Wallpapers`), as many as you add, as HEIC up to 6144 px: sharp on a 6K screen, without keeping a camera's whole picture | Offline and private: no API key, no request per new tab, as Unsplash or Bing would need. CC0 needs no credit on screen and no licence to ship with it |
| 22 | Performance | Measured, not guessed (the timings in older decisions and the audits came from the earlier benchmark, `bench.sh`, removed 2026-11-25): a record kept all the time, in memory (`Recorder.swift`), holds the last five minutes of how long each tab open, switch and close, Back or Forward and first paint took, and every main-thread hitch of 100 ms or more; a watchdog (`Watchdog.swift`) that watches the main run loop from inside writes each stall of a second or more with the main thread's stack, taken a second into the stall, to `stalls.log` in the data folder. Its one timer, in the kernel, is moved on at each step of the main loop and taken off while the loop sleeps, so it never fires while the loop keeps moving or rests, only a second into a real stall. Tab operations are also signpost intervals for Instruments. Both go along only with a feedback report the owner reads and sends; `NERDA_RECORDER=0` turns them off for a run, and each speed-up has its own `NERDA_` switch (`Speedups.swift`) to compare it on and off on one build. WebKit is set up as Safari has it, through SPI that falls back to plain WebKit if it goes: one process pool for every tab, a page process kept ready, sites connected to while their address is typed, DNS prefetch, hidden pages' timers slowed more the longer they stay hidden, a background CPU limit that puts a runaway hidden tab to sleep, and service workers ended 30 s after pages sleep or close only while no extension is loaded (the SPI ends all workers, including extension backgrounds). Each launch keeps its moments from the process start (main, launched, window, shown, first page) and the five launches before it; its stages are `launch` signpost intervals, and work the first window doesn't need (the updater, warming a page's process, removing deleted profiles' data) waits for the first page drawn in the tab on screen (WebKit's first paint, or 3 s after the window if it never comes) and then runs one piece per run-loop turn (Launch.swift). MetricKit's hang reports are kept beside its crash reports, and both go with a feedback report | Left alone, each tab made its own pool and read every font on the Mac first (~30 ms on the main thread per tab); the rest is what keeps Safari quick and light |
| 23 | Frame rate | Pages drawn at the screen's own rate, up to 120 a second on a ProMotion screen, as in Chrome; in Low Power Mode, WebKit's 60, as in Safari. Through SPI (the `PreferPageRenderingUpdatesNear60FPSEnabled` feature flag), set as each page is made | WebKit holds pages near 60 even on a 120 Hz screen, where Chrome, Arc and Firefox draw at 120. A page that is standing still costs nothing either way; one that animates draws twice as often. Measured (`./bench.sh`, a canvas redrawn every frame): 60 → 120 frames a second for 28% → 43% CPU, so Low Power Mode keeps it at 60 |
| 24 | Incognito | A window of its own (`Incognito.swift`), its tabs on a `WKWebsiteDataStore.nonPersistent()` shared by all incognito windows until the last closes, as in Chrome; no history, session or icons written, and nothing from history suggested. Always dark, on a plain grey in place of the glass, with a muted violet accent. They lock together (screen lock, sleep, a minute in the background) behind `LocalAuthentication` (Touch ID or the Mac's password), as Safari's private windows do | WebKit keeps a non-persistent store's cookies, cache and storage in memory only; the look makes it plain which window is private |
| 25 | Trying it on screen | On this Mac, in the background: Nerda Test (`./build.sh test`, data of its own) opens behind the window in use and is driven through its window's accessibility elements with cua-driver (trycua/cua, MIT, telemetry off), never with the pointer, the keyboard or by coming forward (AGENTS.md has the how). Pictures of changes are welcome in a pull request, not required | Agents took the owner's screen, mouse and keyboard in the middle of a video or a chat (Orca), so that stays ruled out. A test VM (Tart) did it apart, but its 4 GB of memory, 67 GB of disk and one-agent-at-a-time waits weighed on the work more than they saved: removed 2026-09-26. cua-driver posts to one app's window and reads its accessibility tree, which leaves the owner's pointer and front app as they are (checked); a click by position into a page doesn't land, so tests go by element |
| 26 | Direction | Nerda grows into one place to work from without leaving it, as a universal tool: it fits around the services and apps people already use (their web apps, accounts, files) and ties them together, rather than building its own mail, chat, calendar or the like | Rebuilding existing products is years of work and would break the lightweight goal (#2, #12); the web apps are already there, what's missing is one place that holds them together |
| 27 | Bookmarks | As in Arc: a bookmark opens in a tab of its own that stays in the bookmark's place (`Tab.bookmark`), not in the list; closing it keeps the bookmark, which opens afresh at its address. Folders nest. Kept in `bookmarks.json`, written whole on each change. Imported from the Netscape HTML file every browser exports | Keeping tabs to come back to was what was asked for, not a list of links that open new tabs. One HTML format covers Chrome, Safari, Firefox and Arc; reading Safari's own file would need Full Disk Access |
| 28 | Text selection | Drawn as Chrome draws it, on the text only (`Selection.swift`): WebKit's own selection colour is made clear by a user style sheet (SPI), and the selection is drawn as a CSS Custom Highlight in WebKit's colours. A site's own `::selection` colour, text fields, images and the insides of components stay WebKit's to draw | WebKit fills a selection's gaps out to the page's edges and between blocks, and has no setting against it (checked in its source: the old `SelectionPaintingWithoutSelectionGaps` setting is gone). A page highlight colours text only |
| 29 | Feedback and crashes | Help › Report a Problem… and Suggest an Idea…, and a card in the sidebar after a crash, show the report and, once the person continues, open a new GitHub issue in a tab, filled in for them to finish and submit (`Feedback.swift`). The report travels in the issue page's address, so it reaches GitHub as that page opens: the preview comes first for that reason. Crashes come from MetricKit at the next launch; each release carries its `Nerda.dSYM.zip` for `symbolicate.sh` | No server, account or key of Nerda's (#10, #12), and nothing leaves the Mac before the person has seen it and continued. GitHub needs an account of the person's own, the price of not running a server |
| 30 | Translation | Apple's Translation framework, on this Mac (`Translate.swift`), as Safari translates. The page's language is what its `<html lang>` says, or else NaturalLanguage's guess from its first thousand characters; a page in none of your languages (Settings › General) gets a Translate button in the address bar and View › Translation. Nerda's script, in its own world, sends the page's text a block at a time (a paragraph, a list item, a cell: the inline content between blocks), its links, bold and code marked by number, `⟦1⟧…⟦/1⟧`, and puts each element back round its own words in the translation's order; marks that come back broken leave the sentence whole without its links. Ten blocks or 500 characters a batch, nearest the screen first and the page's `main` before its menus, tooltips and alt text last, each written back as it comes; it takes up what the page adds, and puts back the very nodes and words for Show Original; at most 100,000 characters a page. The session comes from SwiftUI's `translationTask`, one per window for the tab on screen; a tab keeps translating the pages it opens until Show Original | Nothing leaves the Mac and there is no server, account or key (#10, #12). `translationTask` works from macOS 15 and lets the Mac ask to download a language itself; macOS 26's `TranslationSession(installedSource:target:)` only takes languages already downloaded. The top frame only, as frames are other sites'. Text node by text node, a sentence split by links came back in pieces ("one Web browser Or one Web browser"); the model keeps the marks (241 of 241 blocks of French and German Wikipedia, taking a close written `⟧/1⟧` and a lost empty mark). Measured on an M1 Pro with the high-fidelity model macOS 26.4 uses by default (`.lowLatency` was not downloaded): about 60 characters a second, one request after another whether sent singly, in batches or side by side, so the first screen of a Wikipedia article (about 3,000 characters) takes 45-55 seconds; small batches only decide what comes first |
| 31 | Reader | Nerda's own article extractor (`Reader.swift`), in JavaScript run in a content world of Nerda's: each paragraph scores the box it sits in by its length and commas, less what of it is links, with names like article, content or post counting for a box and comment, sidebar, nav, share or related against it; the best box, and those beside it that score near it, are copied into a page of Nerda's tag by tag from a short list (lazy-loaded images at their real address), with the title, byline, site and date from the page's meta tags and JSON-LD. A small check after each page loads, when the page is idle, decides whether to offer it. The article shows over the tab's page in a view of its own with no scripts and a strict CSP, as Safari's Reader takes the page's place | Mozilla's Readability is the usual answer, but it is a dependency (#12), and much larger than what is needed here; Safari's own Reader isn't open to other apps. Over the page rather than in it, the site's scripts and styles can't reach the article, and leaving Reader is instant: the page under it was never reloaded |
| 32 | Import from a browser | File › Import From Browser… reads another browser's own files on this Mac (`BrowserImport.swift`): a copy of each SQLite file (Chromium's History, Firefox's places.sqlite) read with the system's SQLite, and Chromium's Bookmarks JSON. History is merged into Nerda's (counts added, the later date kept), no older than Settings keeps it and no more than its limit; bookmarks go in a folder of their own. Safari's history is not read | No export step for the person, and no dependency: SQLite ships with macOS. A copy, as the browser keeps its files open and locked. Safari's files need Full Disk Access, too much to ask for an import; its bookmarks come from the file it exports (#27) |
| 33 | AutoFill | Addresses and cards are Nerda's own: `autofill.json` beside `accounts.json`, and the card numbers one item in the login keychain (`Nerda Cards`), as passwords are (#11), each profile its own (#34); a card's security code is never kept. The passwords' script, in the same script world, tells a form's boxes by their `autocomplete` token or else the English words in their name, id and label, lists what is kept under the box the caret is in, and fills that run of the form (`AutoFill.swift`). Only the top frame and frames of its origin; cards only over https, and only after Touch ID or the Mac's password. A form's new address or card is offered to keep once the next page loads, never in incognito. Settings › AutoFill turns each on or off and edits them | One script, one list under a box and one keychain question per build, as for passwords; everything but the number outside the keychain, so listing and the settings never ask it. A frame from another site (an ad, a payment provider's) is not the page's to fill |
| 34 | Profiles | As in Safari: Settings › Profiles makes one, with a name, a symbol and a colour, and renames or deletes it. Each keeps its history, bookmarks, open tabs, site settings, addresses and cards and the names of its saved passwords in a folder of its own (`Profiles/<id>`), its cookies and website data in a `WKWebsiteDataStore(forIdentifier:)`, and its passwords and card numbers in keychain items of its own (`Profile.swift`). Personal, the first, keeps what there was before profiles where it was, so nothing moves. One window a profile, as Nerda has one regular window: File › New Window and the top of the sidebar's menu open it, and ⌘N (File › New Window) brings the window of the profile in front, or else of the one used last, forward on a new tab, opening it again if it was closed: a profile has no second window to open, its menu button wears the profile's symbol, and those left open come back at launch. Links from other apps open in the window of a profile used last. Deleting one closes its window and removes its folder, keychain items and data store. With Personal alone none of this shows or runs, but Settings › Profiles. Nerda's own settings, downloads and the new tab's pictures are shared by all | Work and personal accounts of one site signed in side by side, with no account or server (#10). A keychain item each rather than a profile tag in one: the vault writes its item whole and keeps only the logins its own names list, so two profiles in one item would each wipe the other's; with an item each the vault stays as it is, and deleting a profile's passwords is one call. A store per identifier is WebKit's own way, from macOS 14, to keep cookies, cache and storage apart on disk |
| 35 | Moving a tab to a window of its own | Move to New Window (a tab's menu, Window menu) or a tab dragged off its window makes a secondary window of the same browsing (`Browser.isSecondary`, `Windows.moveToNewWindow`), filling the display it is let go on, or from the menu the next display. The `Tab` object moves with its `WKWebView`, which is never reloaded. A secondary window shows tabs only: the pinned sites and bookmarks stay in the profile's own window, and settings, history and bookmarks opened from it go there. A pinned site or a bookmark's tab moved out leaves its tile or row behind, asleep. Dragged off its list, the tab's place closes up and a card of it (the hover card's) follows the pointer in a panel of its own across displays; over another window's tabs a gap opens with the tab in it, and it lands there (`TabDrag`). A tab let go on another window of the same browsing joins it; Window › Merge All Windows brings them back. Each secondary window is saved with its frame (`<profile folder>/Windows/<id>.json`) and opens again on its display at launch; closing one puts it in the profile window's Recently Closed as one entry (Window with N Tabs, as Chrome lists a closed window), which opens it again with all its tabs, rather than an entry a tab that would push the tabs closed before out of the last 25 | For several displays, as every browser allows. Arc, Zen and Safari show the pinned tabs in every window, which keeps a page of each pinned site per window and doubles their memory; Chrome ties them to the window they were pinned in. One home for pins and bookmarks keeps one page each. Moving the page rather than reopening its address keeps a video playing and a form's text |
| 36 | Video files | A video or sound file a page's script gives another site's https address (`src` or `setAttribute` on a `<video>`, `<audio>` or its `<source>`) is handed to WebKit as `nerda-media:` (`MediaCache.swift`). Nerda fetches it in 8 MB ranges, the next before playback gets there (16 MB ahead), with what WebKit would send (the page's browser name, the frame's origin as referrer, cookies only of the tab's own site), and keeps the bytes in a temporary folder while it runs, 2 GB at most. The page reads back its own address (`src`, `currentSrc`, `getAttribute`); one that fails before playing (a Content Security Policy, a server without ranges, an expired address) is loaded from its own address again. Left as WebKit has them: streams a player builds (MSE, `blob:`), HLS, the page's own origin, elements asking for CORS, and incognito | WebKit hands such a file to AVFoundation, which keeps only what is ahead of the playhead, and WebKit's cache keeps no media (`NoDueToStreamingMedia`): every step back asked the server again, and a 1080p file (5 Mbit/s) from a server giving about 6 waited and stuttered after each one; Chrome keeps what it loaded. Measured on asilmedia.org (1080p, page muted), a step back to what had played: 0.5 to 2.1 s before, 0.05 s after. AVFoundation reads a scheme handler's file a few bytes at a time, so ranges are fetched ahead, one at a time, rather than per read |
| 37 | Where a window opens | Each profile's own window opens where and at the size it was left, as in Safari and Chrome (`WindowFrame.swift`, in the defaults by the profile's id, kept as it is moved or resized). The first time, it fills the screen short of the menu bar and Dock; left filling it, it fills it again, whatever size that is now, and follows the Dock as it hides or shows; left on a display no longer there, or bigger than the one it is on, it fills the main screen, or that one; partly off a screen, it is moved all onto it. Full screen is never kept: a window quit in it opens at the frame it had before. An incognito window opens where the regular one was left, down and to the right of a window already there. A tab moved to a window of its own fills its display (#35) | Every window filling the screen at each launch kept one stray resize from sticking, but threw away a size chosen on purpose, which every other browser keeps. Saving only the frame a person left, with whether it was filling the screen, keeps both: a window left full keeps filling the screen as the Dock and displays change |
| 38 | The window's buttons | Close, minimise and zoom sit on the sidebar, and go with it, as in Arc: they leave as it starts to go and come once it is in, and stay across the top with the tabs there, and over an incognito window's lock. With the sidebar put away, they come while the pointer is anywhere in the title bar along the window's top, and go once it leaves, without the sidebar coming out (`TrafficLights` in `main.swift`, a tracking area that takes no clicks) | Hidden with the sidebar, the window could be closed or zoomed only from the menus or keys, or by bringing the sidebar out from the left edge first. | 39 | Spare page | Each regular data store (Personal's, each profile's, from when its window is made) keeps one spare page (`SparePages.swift`): a blank page built from the same configuration a tab's page is, its process started at once with WebKit's private `_launchInitialProcessIfNecessary` behind `responds(to:)` (without it, the page is still built ahead and its process starts at its first load). The next page a tab of that store makes for the web takes it: a new tab's (⌘T) once it goes somewhere, a link opened in a new tab, a sleeping tab woken. Pages a page opens come on WebKit's own configuration, and extensions' pages on theirs, so they never take it. The next spare is made 1.5 s after one is taken, on a timer in the run loop's default mode only, never in a drag or a scroll. The first is made at launch, once the first page is in, in place of the pool's warmed process (`Tab.warmUp`, still asked for after each page). None in Low Power Mode or under critical memory pressure (it goes as either comes and comes back after), none for incognito, whose store is in memory; a profile's goes when its last window closes, or it is deleted, and comes back when its window is shown. `NERDA_SPARE_PAGE=0` turns it off for one run (spec #118). | A new tab started its page and its process only when asked for, and that moment showed. Yab, from the same Search fork, measured 101–116 ms → 60–66 ms per new tab with one, for about 10 MB; a page made in the spare's process is under way at once. |
| 40 | Hidden pages keep running | A page out of sight keeps running (WebKit's `inactiveSchedulingPolicy` `.none`), where WebKit and Safari suspend it; in Low Power Mode it is suspended (`.suspend`), as before. Its timers stay slowed the longer it is hidden and the background CPU limit stays (#22). WebKit reads the policy only as a page joins its process (seen on macOS 27 and in WebKit's `WebProcessProxy::addExistingWebPage`), so when the mode changes each page process gets one more page, made in it through `_setRelatedWebView:` and let go at once, and reads it again; without that SPI an open page follows once it is made again. `NERDA_HIDDEN_RUN=0` leaves WebKit's own for a run (`Tab.hiddenPolicy`) | Switching back to a suspended page waits for it to wake: Yab measured the slowest tenth of switches going from 128 ms to 66 ms with pages left running, while 48 open sites out of sight went from 11% to 35% of a core. Chats, dashboards and players carry on out of sight. Low Power Mode is where the owner has asked for battery over speed |
| 41 | Last frame on switch | When a tab goes out of sight, its page's last frame is pictured by WebKit (`takeSnapshot`), drawn off the main thread into an IOSurface and kept in memory only, at most a share of the Mac's memory between 48 and 256 MB, the oldest going first and all of them under memory pressure. Switching back puts it over the page in the same frame as the switch (`LastFrame.swift`, one per `PageSlot`) and takes it down once WebKit has drawn the page (`_doAfterNextPresentationUpdate:`, else a one-point snapshot) or after 2 s. It is used only when the address, size, scale, zoom, appearance and scroll position are as they were; a page that scrolls or changes height after its frame was taken says so at once, from a script in Nerda's own world, and its frame is let go before it can be shown; as a last check, scroll is also asked of the page as it comes back, and the frame goes when it differs. Separate from the hover card's picture, which outlives the page. `NERDA_LAST_FRAME=0` turns it off for a run | A page coming back can show nothing until WebKit has drawn it again, a moment for an idle page and longer for a busy one. A frame drawn for another size, zoom, appearance or scroll would show a page that isn't there; the window server shows an IOSurface without a copy, so putting it up costs the switch nothing. Yab's design (Apache-2.0), from the same Search code |
| 42 | Hung pages and repeated crashes | A page counts as not answering once WebKit says so (`_webViewWebProcessDidBecomeUnresponsive`, three seconds after an input or load it didn't take) and two pings in a row, `evaluateJavaScript` given 2 s each, go unanswered (`HungPages.swift`). On screen, 12 s after WebKit's word, so 15 s after the owner reached for it, a card asks Wait or Reload; Wait keeps it away 30 s, until the next click or key, and it goes by itself if the page answers. Reload, closing the tab, an address typed, Back, Forward (from the menu, a swipe or a mouse's buttons) and sleep first take such a page away from its tab, history kept, and end its process (`_killWebContentProcess`, then SIGKILL a second later if the same process still runs), so the tab goes on at once in a fresh page. Out of sight, once a minute, a page that kept a quarter of a core busy since the last look (`proc_pid_rusage`) is pinged; two unanswered, it is ended and put to sleep, unless it holds something typed or plays sound, which is asked about when shown. `NERDA_HANG_HANDLING=0` turns it off for a run. When a page's process ends, Nerda reads why from WebKit's private termination callback (memory, CPU, asked for, crash; `PageEnds.swift`), falling back to the public one, which gives no reason. Ends within 0.1 s of each other, in any window, are one shared cause and count for none of their pages; an end asked for (WebKit swapping a process) or Nerda's own (`Tab.endingOnPurpose`, set before it ends a hung page on every tab of any window that shares its process) never counts. A page WebKit calls unresponsive that still answers is no hung page: nothing is ended, and its changes are asked about as any page's are. A page that ends alone three times in a minute is not loaded again: it says it crashed, or ran out of memory, each time it was opened, and ⌘R tries again. Otherwise the page on screen reloads at once and one out of sight sleeps until shown; a page with something typed into it says so at once | A page in a loop takes in nothing, not ⌘R nor the request to end that closing its view sends, so one site held its tab and Nerda looked frozen. WebKit's termination call alone was seen to leave such a process running on macOS 27; SIGKILL ends it. The pings tell a hung page from one busy for a moment, and a page working on purpose (in a worker) answers them. WebKit says nothing of a hidden page spinning (nothing in 90 s, tested), and its CPU limit (#22) takes 8 minutes. Taking the page away before its process ends means nothing waits for the process to go. This is Yab's design (Deaf.swift, Stuck.swift). One page dying twice in a minute stopped it, so a WebKit GPU or network process going down, or memory running out, which ends every page together, could stop several tabs that had done nothing wrong; and a page reloaded straight after a crash often crashes once more for the same passing reason. Three ends alone in a minute is Yab's rule, from the same Search code |
| 43 | Agent control | Agents (Claude Code, Codex) drive Nerda through its own MCP server, not AppleScript, a browser extension or Chrome's DevTools protocol (spec #119). The app listens on a Unix socket in its edition's data folder (`agents.sock`), owner-only, a large backlog, one request a connection as one line of JSON with a size cap (1 MB) and a deadline (25 s unless the verb says otherwise), read and answered off the main thread, the verb itself done on it (`AgentServer`, `AgentSocket`). Each request carries a wire version; a mismatch answers "reopen Nerda". Callers are checked by user id, then by audit token their code signature against Nerda's own designated requirement, kept per token; development and test builds skip the signature check (`AgentCallers`). Any other signed program, told apart by its own designated requirement, which its signature must meet, gets status only until the owner allows it on a sheet over their window, which doesn't bring Nerda forward: Allow once (until Nerda quits), Always or Don't allow, one question per program however often it calls; Always and Don't allow are kept and listed in Settings › Security & Privacy › Agents, to be removed (`AgentApprovals`, #132). An unsigned program gets status only. `Nerda mcp` is a stateless stdio proxy: each tool call is one socket request, for the Agent session named by the MCP client's name and the session id its harness exports (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`), so an agent's many connections are one session (`AgentMCP`). The verbs are one table (`AgentVerb.all`) the app answers from and the shim lists as tools. An agent picks the profile by name (`profiles` says which one has sign-in cookies for a site). Agent tabs live in an Agent browser of the profile, off screen (`AgentBrowser`, #129); a session reaches only the tabs it opened, by short names (t1) never used twice, so another session's tabs, the owner's and incognito are out of its reach (`AgentSessions`). Settings › Security & Privacy › Agents can use Nerda, on by default, takes the socket away. Cleanup (#146): a session that has asked for nothing for 15 minutes of awake time (`SuspendingClock`, swept once a minute) is finished, detached or not, and its tabs close, but those holding something typed (`Tab.hasUnsavedWork`) or kept by the owner; a later call on one answers that it was closed after its session ended (`AgentCleanup.swift`). The shim tells the app when its client closes stdin, and the session detaches until its next request. With Nerda closed, the shim or the `nerda-browser` command starts it with `--hidden-for-agents`, not made active: no Dock tile (`.accessory`), no window, no tabs restored; it quits after 30 idle minutes, and opening it by hand shows it as any launch. It never hides itself as an app (`NSApp.hide`, `open -j`), since WebKit takes a hidden app's pages as hidden (`AgentLauncher`, `HiddenStart`, #133). Awake (#135): while a session works and for 2 minutes after its last request, its tabs' pages have WebKit's window occlusion detection off (`hearsWindowCovered`, SPI behind `responds(to:)`), so the off-screen window's pages count as in sight, and no sleep rule takes them (`Tab.isKeptAwake`); awake Agent tabs of all sessions are capped at a quarter of the RAM in GB, 6 to 16, the longest unused (of quiet sessions first) put to sleep past it, and woken when asked for again (`AgentAwake`). `screenshot` is the viewport by `takeSnapshot`, 1024 pixels wide as a JPEG or at full resolution; `click_at` turns a point of it into mouse events sent to the page view. `sign_in` (#147) fills a login from the profile's vault with the owner's own fill script (`nerdaFill`, in `Passwords.world`), into the first frame asking for a password, else for a name alone, on the frame's site as the list under a sign-in box offers it (only logins last used over http on an http page); the password goes from the vault into that world only, the agent is told which name went in, and the owner isn't asked each time (`AgentSignIn`). Site skills (#149): Markdown files with a name, a description and the sites they cover on top; Nerda's own are compiled into the app (`BuiltInSkills.swift`), the owner's are `Skills/<name>.md` in the data folder, read each time, one of the same name winning over Nerda's. The first answer of a session on a covered host (or one under it) carries a `skill:` header line, once per skill and session. `skill` and `skill_save` are the skills group; `skill_save` refuses a file over 20,000 characters, then waits on the owner as a Handoff does, and writes the file only once the owner presses Save on a sheet over their window showing the whole file (`SiteSkills`) | Agents work in the owner's own browser, signed in as they are, without taking the window or the keyboard (Ardia's agent control wasn't smooth or reliable enough). One request a connection keeps the shim stateless, so an update, a killed process or a crashed app never leaves a connection stuck; the wire version is there because Yab's shim broke after updates. The shim is the app's own binary, so it meets the app's designated requirement by construction, and nothing else running as the owner drives a signed-in browser unasked. Idle time ends a session, not only a detach, because a killed shim never says it went away; a night's sleep is no time unused. A cleaned-up tab answering only "no tab" left Yab's agents guessing.
