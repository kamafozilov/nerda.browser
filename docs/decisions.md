# Technical decisions

Reference: [driceroland/Search](https://github.com/driceroland/Search) (MIT). We follow the same path.

## Adopted

| # | Layer | Decision | Why |
|---|---|---|---|
| 1 | Platform | macOS only | I use macOS myself; on Windows/Linux, Chrome extensions only fully work with Chromium, which goes against the "lightweight" goal |
| 2 | Engine | WebKit (`WKWebView`) | Ships with the system: the app is a few MB, without Chromium's 300 MB |
| 3 | Language | Swift | The only natural choice for Apple APIs |
| 4 | UI | SwiftUI, plus AppKit where needed | Search does it this way and it works |
| 5 | Project | SwiftPM (`Package.swift`) + `build.sh` assembles the `.app` bundle | Plain text files only; Xcode not required (Command Line Tools are enough) |
| 6 | Minimum OS | macOS 15.4 | `WKWebExtensionController` exists from this version on (checked in a build) |
| 7 | Chrome extensions | `WKWebExtension` + installing `.crx` from the Chrome Web Store | That is where the main users come from |
| 8 | Ad blocking | EasyList and EasyPrivacy network filters compiled to `WKContentRuleList` in a helper process, refreshed every 4 days. Main-frame navigation is always allowed; generic blocks apply only to third-party requests, and known challenge services are exempt. Settings can disable blocking. See [adblock audit](adblock-audit.md) for translation limits and evidence | WebKit filters requests without per-request Swift or JavaScript. Versioned compiled caches prevent reuse of unsafe rules; failed updates keep the last compatible list, and navigation never waits for a download. Cosmetic rules and scriptlets are not supported |
| 9 | RAM | Put unused tabs to sleep (the web view is destroyed, a snapshot stays); sooner under memory pressure. Pinned tabs never sleep and load right away at launch | 100–300 MB per tab is the main cost |
| 10 | Storage | JSON files, in one folder | No server, no account |
| 11 | Passwords | Nerda's own store: the passwords are one item in the login keychain (`Nerda Passwords`), the site and user names they go with are `accounts.json` beside the history; those in Passwords/Safari come in once from a CSV via File › Import Passwords… | Safari's passwords sit behind an Apple entitlement; macOS (AMFI launch constraint) won't start the iCloud Passwords helper from Nerda. The keychain asks again after every build without a Team ID: as one item, and with the names outside it, that is one question, and only once a password is picked or saved, never for listing accounts |
| 12 | External dependencies | None, Apple frameworks only | |
| 13 | Codebase | Written from scratch; needed parts (e.g. `Crx.swift`, `ExtensionShims.swift`) are taken from Search, with the MIT license text | The structure should be our own |
| 14 | Tools | Xcode (Instruments, debugger), `swift format` (in the toolchain) | Command Line Tools are enough to build |
| 15 | Entry point | AppKit (`NSApplication`, `main.swift`); SwiftUI views through `NSHostingView` | Full control over windows; a SwiftUI `App` always requires some Scene |
| 16 | Concurrency | Swift 6, default isolation `MainActor` | AppKit and WebKit are on the main thread anyway; background work is marked explicitly |
| 17 | Versions | SemVer tags `vX.Y.Z`; 0.0.x, one patch step per release, until the public launch as 1.0.0; `CHANGELOG.md` in Keep a Changelog form | See [releasing.md](releasing.md) |
| 18 | Dev and release | Nerda Dev (debug) is a separate app: its own bundle id, data folder and keychain item (`Edition.swift`, `build.sh`) | Working on Nerda must not touch the data of the Nerda in use |
| 19 | Updates | Our own updater (`Updater.swift`, after Search's): GitHub Releases carry the DMG and a ZIP; a newer ZIP is checked by SHA-256, bundle id, version and a Developer ID signature of the same team, then swapped in | No framework (#12): Sparkle would add a framework, an EdDSA key and a copy step to build.sh, for what about 300 lines do |
| 20 | Signing | Releases: Developer ID Application, one fixed team (`NERDA_TEAM` in the untracked `release.env`), hardened runtime, notarized and stapled, universal (arm64 + x86_64). Development: the Apple Development certificate, as before | Opens on any Mac without warnings; the team is fixed because the updater only accepts its own |
| 21 | New tab pictures | CC0 photos from Wikimedia Commons, bundled (`assets/backgrounds`, credits there), 2880 px HEIC, one for now, more as they are chosen; one a day, decoded once off the main thread, big enough to fill the largest screen. Your pictures are copied into the data folder (`Wallpapers`), as many as you add, as HEIC up to 6144 px: sharp on a 6K screen, without keeping a camera's whole picture | Offline and private: no API key, no request per new tab, as Unsplash or Bing would need. CC0 needs no credit on screen and no licence to ship with it |
| 22 | Performance | Measured, not guessed: `./bench.sh` (Bench.swift) times launch, pages opening, tab switches and wakes, typing in the address bar, memory and CPU at rest (`./bench.sh web` adds Speedometer, JetStream, MotionMark). WebKit is set up as Safari has it, through SPI that falls back to plain WebKit if it goes: one process pool for every tab, a page process kept ready, sites connected to while their address is typed, DNS prefetch, hidden pages' timers slowed more the longer they stay hidden, a background CPU limit that puts a runaway hidden tab to sleep, and sites' idle service workers ended 30 s after their pages sleep or close, as Chrome ends idle ones | Left alone, each tab made its own pool and read every font on the Mac first (~30 ms on the main thread per tab); the rest is what keeps Safari quick and light |
| 23 | Frame rate | Pages drawn at the screen's own rate, up to 120 a second on a ProMotion screen, as in Chrome; in Low Power Mode, WebKit's 60, as in Safari. Through SPI (the `PreferPageRenderingUpdatesNear60FPSEnabled` feature flag), set as each page is made | WebKit holds pages near 60 even on a 120 Hz screen, where Chrome, Arc and Firefox draw at 120. A page that is standing still costs nothing either way; one that animates draws twice as often. Measured (`./bench.sh`, a canvas redrawn every frame): 60 → 120 frames a second for 28% → 43% CPU, so Low Power Mode keeps it at 60 |
| 24 | Incognito | A window of its own (`Incognito.swift`), its tabs on a `WKWebsiteDataStore.nonPersistent()` shared by all incognito windows until the last closes, as in Chrome; no history, session or icons written, and nothing from history suggested. Always dark, on a plain grey in place of the glass, with a muted violet accent. They lock together (screen lock, sleep, a minute in the background) behind `LocalAuthentication` (Touch ID or the Mac's password), as Safari's private windows do | WebKit keeps a non-persistent store's cookies, cache and storage in memory only; the look makes it plain which window is private |
| 25 | Trying it on screen | A macOS 27 VM (Tart, Cirrus Labs' image) that shows no window here, driven by `vm.sh`: Nerda Dev copied in and opened there, mouse, keys and screenshots through the hypervisor's own VNC server (vncdotool), suspended between uses. On the Mac itself Nerda Dev opens behind the window in use | Agents testing on the owner's Mac took its screen, mouse and keyboard, in the middle of a video or a chat. The VM has its own; VNC at the hypervisor needs no Accessibility or Screen Recording permission inside it. Suspended, it frees its 4 GB and wakes in seconds. Tart and vncdotool are tools of the work, not of the app (#12) |

## Known limitations

- Extensions at Safari's level: `webRequest` doesn't work in MV3; some (e.g. Vimium C) don't open.
- DRM: FairPlay only (Netflix etc. as in Safari).
- Full screen: inside the window, as in Chrome (WebKit's own moves the page into a separate window and can't be turned off). A site's own `:fullscreen` CSS rules don't apply; the button of a plain `<video controls>` still opens WebKit's separate window. WebKit SPI (`_setWindowOcclusionDetectionEnabled:`) keeps video playing during the full-screen animation; should it go away, video only pauses for a moment during the animation again.
- Address bar colour: taken from WebKit's own sample of the page's top edge (SPI `_sampledPageTopColor`, as Safari's); should it go away, the bar falls back to the page's `theme-color`, which some sites (GitHub, YouTube) set to a colour their top doesn't use.
- Page edges: a page scrolled to its end stays put, as in Chrome, through WebKit SPI (`_setRubberBandingEnabled:`, as each page is made); should it go away, pages bounce past their edges again. A box that scrolls inside a page (a chat, a code view) still bounces: WebKit gives no switch for those.
- Passwords: only in the page's own frame (not in sign-ins inside another site's iframe). No passkeys (they need Apple's browser entitlement and a Developer ID). Without an Apple Development certificate (Team ID), macOS asks for the login password once after each new build, the first time a password is picked or saved; `build.sh` uses the certificate by itself when there is one.
